USER:
Reported a third error: "Supabase insert failed: Forbidden use of secret API
key in browser."

--------------------------------------------------------------------------------
ASSISTANT:
Explained this is Supabase's newer "secret key" safety check, which blocks
requests that look like they're coming from a browser — and that Apps
Script's UrlFetchApp sends a default User-Agent starting with "Mozilla/5.0",
tripping that heuristic even for a legitimate server-side call. Fixed by
overriding the User-Agent header (to a custom, non-browser-looking value) on
both Supabase fetch calls, and additionally suggested a fallback: switching
to a legacy service_role JWT key (format eyJ...) instead of the new
sb_secret_... key, since legacy JWTs aren't subject to that specific check.

--------------------------------------------------------------------------------
USER:
Said they replaced the key with a "legacy JWT key" but it didn't start with
"eyJ", and got a new error: "Invalid API key."

--------------------------------------------------------------------------------
ASSISTANT:
Used the Supabase MCP tool to confirm the project does have an active legacy
anon key (a real JWT starting with eyJ, decodable to role: "anon"), meaning a
legacy service_role key should exist alongside it on the same dashboard page.
Concluded the user had likely copied the "JWT Secret" (the signing secret,
found in a different section of the same Settings page) instead of the actual
service_role token, and pointed them to the correct location: Project
Settings → API Keys → Legacy API Keys → the service_role/secret entry, which
should also start with eyJ.
